# Web app updates of 11 October 2026: data contract

These are the client's "Web App updates 11/10/2026" (§1 to §7 below), mapped onto the data layer. Every page builds on the
functions and fields listed here. **Only `js/store.js`, `js/pricing.js`, `js/geo.js` and `js/seed.js` define them; pages never
re-implement the rules.** All store calls return Promises; `MDM.store._list(col)` / `_settings()` are synchronous reads.

## Orientation (for anyone new to the codebase)

- Static vanilla HTML/CSS/JS, no build. Every page loads, deferred and in order: `js/mdm.js, icons.js, store.js, roads.js,
  geo.js, pricing.js, map.js, live.js, ui.js, shell.js, [package-editor.js], seed.js`, then the page's own `page.js`.
- Shared helpers: `MDM.ui` (`el`, `html`, `esc`, `qs`, `on`, `toast`, `dialog`, `confirm`, `drawer`, `field`, `money`, `fmtDate`,
  `fmtTime`, `timeAgo`, `phone.normalize/format/valid`, `fileToDataUrl`, `imageToJpeg`, `plural`, `statusBadge`, `paymentBadge`),
  `MDM.badgeFor(status, {customer})`, `MDM.payBadge(status)`, `MDM.codBadge(status)`, `MDM.icon(name, size)`, `MDM.href(path)`.
- Styling: tokens and components in `css/base.css` + `css/pages.css` (`.btn`, `.btn--primary/--brand/--ghost/--sm`, `.field`,
  `.input`, `.select`, `.textarea`, `.segmented`, `.card`, `.badge--ok/info/warn/danger/neutral`, `.alert--info/warn/danger`,
  `.table`, `.list`, `.grid-2/3`, `.tabs`). Light and dark themes come from tokens (`--bg`, `--card`, `--text`, `--text-2`,
  `--border`, `--brand` #D2002F); never hard-code colours that break dark mode.
- Design rules: clean red/white/black, plain functional labels (no marketing flourish, no uppercase), mobile-first at 360px, no
  horizontal scroll, 44px tap targets on phones, accessible labels, escape every user-entered string.
- Testing: `node tools/serve.js 4180` serves the parent folder, so pages are at `http://localhost:4180/mr-delivery-man-mockup/…`.
  Playwright: `require(process.env.HOME + '/.npm/_npx/6bcb61ec6d5aea22/node_modules/playwright')`. Put scratch tests in
  `tools/_scratch/` (git-ignored). `bash tools/check.sh` must print nothing. `await MDM.store.reset()` restores the demo data.
- Sessions: customer `localStorage mdm:me {name, phone}`, business `localStorage mdm:business {accountId, name, phone}`, driver
  `sessionStorage mdm:driver {driverId, online}`, staff `localStorage mdm:staff {staffId, name, role}`, office
  `localStorage mdm:session {user, staffId, role: admin|operator|office, name}`. `store.reset()` (and the automatic reseed) keeps

## §1 Service categories

- `MDM.SERVICE_CATEGORIES`: `pick` (Pick & Deliver: home, shop_collect, postal, office), `shop` (Shop & Deliver: shop_buy),
  `business` (Business Delivery: no request types, it is the business portal).
- `MDM.REQUEST_TYPES` labels: `home` Home collection, `shop_collect` Shop or godown collection, `postal` Postal & courier collection,
  `office` Administrative services, `shop_buy` Shop & deliver. `airport` is `legacy: true` (older orders only; airport runs are now a
  delivery method). `MDM.requestTypes(category)` → offered types; `MDM.categoryOf(type)`.
- Shop & deliver orders keep `packages[0].shop = { name, address, zone, list, budget, unavailable }` for pricing and add
  `details.shop = { name, address, zone, phone }`, `details.items = [{ name, details, qty, instructions }]`, `details.budget`.
  The shopping fee is `rates.shoppingPct` % of the budget (then of the receipt), shown as its own line.
- Business account requests (`business_requests`) carry `packagePhotoId` (required: a picture of a typical package) and
  `typicalSize` (`small|medium|large`, the business's own guess).
- Business size categories: `settings.rates.businessTiers` (default `MDM.DEFAULT_BUSINESS_TIERS`:
  small/bag MVR 25 "Fits in a bag, under about 1 ft (30 cm)", medium/box MVR 35 "A carton up to about 2 ft (60 cm) a side",
  large/xl MVR 60, placeholders to confirm with the client; the hints match the customer size guide). Each account has
  `rates: { small: 25, medium: 35 }` and `tiers: ['small', 'medium']` (the agreed categories) plus `packagePhotoId` and `assessment`.
  `MDM.pricing.businessTiers(settings)`, `MDM.pricing.businessRate(account, tier, settings)`,
  `MDM.pricing.accountTiers(account, settings)` → `[{ value, label, size, hint, rate }]` for that account.
  `store.approveBusinessRequest(requestId, { rates: { medium: 38 }, notes, by })` creates the account;
  `store.setBusinessRates(accountId, rates, by)` changes agreed rates.

## §2 Placing an order

- Saved addresses: `customers[].addresses = [{ id, label, address, zone, landmark, meetAt, contactName, contactPhone, notes }]`.
  Labels are free text with presets `MDM.ADDRESS_LABELS` (Home, Wife's home, Office, Other).
  `store.saveAddress(phone, address)` adds or updates (pass `id` to update), `store.removeAddress(phone, id)`.
  Re-order: build a new request from a past order (type, collection, packages, delivery). "Frequently placed" = the customer's most
  common request type + route among their orders, placed at least twice (a tie goes to the most recent): `MDM.frequentRoute(orders)`
  → `{ key, count, latest } | null`, with `MDM.reorderKey(o)`, `MDM.reorderType(o)` (legacy airport → `home`), `MDM.reorderRoute(o)`
  → `{ from, to }` and `MDM.reorderRouteText(o)` (store.js; the request and account pages both use them).
- Package size: Bag / Box / XL plus an optional photo only (no measurements from the customer). Photos go in the `files` collection
  (`{ kind: 'package', orderId, name, type, size, dataUrl }`) and `package.photoId`.
- Extra vehicle: `MDM.extraVehicleEligible(packages)` is true with more than one box or more than one XL. The order flag
  `createOrder({ extraVehicle: true })` marks those packages `needsVehicle` (the price is confirmed first). `order.extraVehicle`
  means only that: the customer asked for it at booking.
  Operators: `store.addVehicleCharge(orderId, { amount, remarks, by })` on any order (adds a `preset: 'vehicle'` adjustment and sets
  `order.vehicleCharged = true`; it never sets `extraVehicle`);
  `store.updatePackages(orderId, { [pkgId]: { size } }, by)` changes a package category and re-prices it (shown to the customer
  once the price is confirmed). Both appear in `pricing.history` and the order events.

## §3 Delivery methods

- `MDM.DELIVERY_METHODS`: `home`, `boat` (boat, ferry or speedboat), `cargo` (Maldivian Cargo), `airport`.
  `MDM.deliveryMethodLabel(v)`. Every order has `delivery.method`.
- Order `delivery` = `{ method, address, zone, landmark, recipientName, recipientPhone, instructions, meetAt, boat, cargo, airport }`:
  - `boat = { vesselType: boat|ferry|speedboat (MDM.VESSEL_TYPES), name, departureDate, departureTime, jetty (MDM.geo.jetties()
    value), island, address (destination address on the island), contact, history: [{ at, by, reason, note, from, to }] }`
  - `cargo = { counter, island, consignee }`: drop at the Maldivian Cargo counter at the main bus terminal
    (`MDM.geo.cargoCounter()`); the MVR 20 cargo fee (`rates.cargo`) applies **only** to this method and is its own fee line.
  - `airport = { point (MDM.geo.airportPoints() value, default resort_counters), counter (resort counter / collection point),
    resort (resort or destination), speedboat (resort speedboat), departureTime, instructions }`; the airport fee applies.
- `createOrder` takes `delivery.method` and the matching object and points every package's drop-off at the jetty / counter /
  airport point (`MDM.deliveryEndpoint(delivery)` does this and is also exported as `store.deliveryEndpoint`).
- Boat details can change after booking (§5.3 note): `store.updateBoat(orderId, { name, departureTime, departureDate, jetty,
  island, vesselType, address, contact }, { reason: MDM.BOAT_CHANGE_REASONS value, note, by })`. It keeps `boat.history`,
  re-points the drop-off when the jetty changes, writes a public `boat_updated` event ('now on speedboat Huraa Speed 2', 'now a
  ferry', 'departs 23:30', 'from Malé North Harbour') and notifies the driver / office / business. The order-level copy follows:
  `delivery.landmark` and `delivery.zone` always take the new endpoint's; `delivery.address` takes the new endpoint address only when
  it was the old endpoint address (or empty), and the new `boat.address` when it was the old one; a receiver's address on the island
  is kept.
- Modify order (`store.modifyOrder(orderId, patch, by)`, any order including bulk children): a changed receiver
  (`delivery.recipientName/recipientPhone`) is copied to every package whose `dropoff.recipient` was the old receiver (or empty),
  to `delivery.boat.contact` when that was the old phone (or empty) and to `delivery.cargo.consignee` when that was the old name
  (both logged in `changes`). A changed collection contact (`collection.contactName/contactPhone`) goes to `pkg.pickup.contact` the
  same way. A changed home address (`delivery.address/zone/landmark`) moves the packages that were at the old address and drops
  their old `lat/lng`; a changed collection address moves the pickups that were at the old one. Packages with their own person or
  address (multi-drop) keep it. If nothing on the route is done the stops are rebuilt; otherwise the stops still to do (`pending`,
  `arrived`, `failed`) take the new contact and, for a home delivery, the new address and point, and `route.polyline` is redrawn
  through the stops not done or skipped.

## §5 Business bulk orders

- Collection points: `business_accounts[].collectionPoints = [{ id, label, address, zone, landmark, contactName, contactPhone,
  preferredTime, isDefault }]`. `store.saveCollectionPoint(accountId, point)`, `store.removeCollectionPoint(accountId, id)`.
- `store.createBatch({ accountId, collection: { pointId, address, zone, landmark, contactName, contactPhone, instructions,
  preferredTime (optional) }, rows, serviceLevel, notes, source: 'portal'|'csv'|'excel', by })` with rows
  `{ name, phone, address, zone, landmark, tier, description, fragile, instructions, reference, cod, method,
  boat | cargo | airport }`. Each row becomes one child order (`requestType: 'bulk'`) priced at the account's agreed rate for
  its tier (`packages[0].tier`, `tierRate`, `price.tier`), with `cod` when the amount is above 0.
- Excel import: the business uploads `.xlsx` (SheetJS from cdnjs, see docs/CDN.md) with columns delivery address, landmark,
  receiver name, contact number, package size (tier), special instructions (+ zone, delivery method, boat fields, cash to collect,
  reference). Validate every row, show the errors, let them fix or drop rows, review, then submit.
- Cancelling one order inside a bulk order: `store.businessCancel(orderId, { reason, by: 'business:<accountId>' })`. Allowed for
  any business order that is not delivered / returned / cancelled. Before collection: cancelled, nothing else to do. After
  collection (`collected`, `out_for_delivery`): cancelled with `cancellation.actionRequired = 'return_to_sender'` and
  `returnStatus = 'pending'`; the driver and the office are notified (notifications with `audience`), the driver sees it in
  `driverRoute(driverId).returns`, and `store.markReturned(orderId, { note, by })` closes it.
- The office cancelling (`store.cancel`, an approved customer request, or `resolveFailure` with `cancel`) works the same way: once a
  pickup stop is done the order gets `cancellation = { …, previousStatus, actionRequired: 'return_to_sender', returnStatus:
  'pending' }` (no return stop is added; the driver uses Returns and `markReturned`), otherwise `actionRequired: 'none',
  returnStatus: null`. The driver (if any) gets an `audience: 'driver'` notification titled `Order cancelled`, and a `pending` COD
  becomes `not_collected` (`note: 'Order cancelled'`). Business cancels have `cancellation.byBusiness: true`, office cancels do not.
- `store.setStop` refuses (`StoreError` code `transition`) any stop on a `cancelled`, `delivered` or `returned` order, except a
  `return` stop on a cancelled order: completing it closes the return task like `markReturned` (`returnStatus: 'done'`, the order
  stays cancelled). `markReturned` also marks any open `return` stop done. When all return stops of an active order are done the
  order becomes `returned` and a `pending` COD becomes `not_collected` (`note: 'Returned to sender'`).
- Bulk order status `store.batchStatus(batch)` / `_batchStatus` → `{ status, total, delivered, out, collected, failed, cancelled,
  amount }` with `status`: `confirmed`, `collected`, `out_for_delivery` (a package is out), `partly_delivered` (some delivered, none
  out, some still to go: a batch-only status, not in `MDM.STATUS`), `delivered` (every package delivered, cancelled or returned)
  or `paid`. `amount` leaves out cancelled packages.
- Cash on delivery (§5.6): `order.cod = { amount, status, collectedAmount, collectedAt, collectedBy, variance, handedAt, handedTo,
  remittedAt, remittedBy, remittanceRef }` with status `pending → collected (with the driver) → with_office → remitted (paid to
  the business)`, or `not_collected`. `MDM.COD_STATUS`, `MDM.codBadge(status)`. Business enters the amount per order (`cod` on a
  row or `createOrder({ cod })`). The driver enters the cash collected on proof of delivery: `setStop(..., { cashCollected })`.
  `cod.collectedBy` is always the driver holding the cash (`driver:<id>`); when the office records the proof of delivery for them,
  `cod.recordedBy` is the office user.
  The office: `store.cashHandover(driverId, { orderIds?, reference, by })` (driver → office) and
  `store.remitCash(accountId, { orderIds?, reference, by })` (office → business). The `cod_remitted` event is `internal` (it names
  the business and the transfer reference, so it is not on the tracking page); the business still gets the "Cash on delivery paid
  to you" notification (order.customer is the business).

## §6 Proof of collection / delivery charges

- `order.charges = [{ id, type: naalu|packing|other (MDM.CHARGE_TYPES), stage: collection|delivery|office, amount, description,
  paidBy: driver|office, billable, adjustmentId, by, at, void }]`.
- Driver on proof of collection: `setStop(orderId, pickupStopId, { status: 'done', photoId, sizes, naalu, naaluNote, remarks })`.
  On proof of delivery: `setStop(orderId, dropStopId, { status: 'done', photoId, recipientName, confirmed, handedTo, remarks,
  naalu, naaluNote, packing, packingNote, cashCollected })`. Naalu is recorded against the stage (collection or delivery) and is
  not charged to the customer unless `settings.rules.naaluBillable` (or the office bills it); packing is billed.
- Office: `store.addCharge(orderId, { type, stage, amount, description (required for other), paidBy, billable, by })`,
  `store.setChargeBillable(orderId, chargeId, true|false, by)`, `store.voidCharge(orderId, chargeId, { reason, by })`. Billable
  charges become price adjustments linked by `adjustmentId`.
- Who is owed a driver-paid charge: the driver who recorded it (`charge.by` = `driver:<id>`), otherwise the order's driver.
  `store.reimburseCharges(driverId, { chargeIds?, reference, by })` uses this rule, so a charge stays with the driver who paid it
  after the order is reassigned (admin/cash.js `driverOfBy` reads it the same way).
- The cargo fee line is labelled `Maldivian Cargo fee` (`× n` when charged per package) wherever `MDM.pricing.quote().feeLines` or
  `MDM.pricing.feeLines(order)` are rendered; invoice lines use the same words.

## §7 Driver logging

- Leave types include `off_day` (Accumulated off day). `store.offDayBalance(staffId)` → `{ opening, earned, adjust, taken,
  balance, overdrawn, weeklyOffDay }`: working the weekly off day (`settings.hr.weeklyOffDay`, 5 = Friday) earns one; approved
  `off_day` leave uses them. `balance` never shows below 0; `overdrawn` is the number of days taken beyond it. `requestLeave`
  refuses more than the balance minus that person's pending `off_day` requests ('Only N accumulated off days left to request');
  `decideLeave` refuses to approve an `off_day` leave longer than the balance ('Only N accumulated off days available').
  `staff[].offDays = { opening, adjust }`.

## Notifications for staff

`notifications` rows with `audience: 'driver' | 'operations' | 'business'` are operational messages (channel `app`); rows without
`audience` went to the end customer. Drivers see theirs by `to === driver.phone`, the office by `audience === 'operations'`.
