# Updates of 10/11/2026 (client, 10/11: changes should show at once)

**Changes show at once on the live service.** In every portal (office, driver, business, customer, staff) a button that changes
something now shows the result straight away: the order moves to Assigned or Dispatched, the remark appears, the payment shows as
received, without waiting for the server. The change goes to the server in the background, one after another in the order they were
made, and the server's answer then takes the place of what the page showed. The page and the server use the same ids, so they are the
same records. If the server refuses a change (someone else changed the order meanwhile, or the role may not do it), the page takes it
back and says "Not saved:" with the reason. A change still on its way when the page is closed or left still reaches the server, and
signing out waits for it.

These still wait for the server, as before:
- placing an order, a bulk order, an e-store order and an invoice, because their numbers come from the database;
- the sign-up step, because it links the sign-in to the customer;
- photos and files, because the upload is the slow part and a failed upload must be seen on the spot, not after the driver has left;
- a change the page's own copy refuses (its rule may need records this page does not hold), so the server's verdict is shown as before.

How it works (`js/store.js` "Changes shown first", `js/remote.js`, `server/runtime.js`):
- The store method runs on the page's copy first. Until the server answers, the copy as the server last confirmed it is kept beside it.
- The answer goes into that confirmed copy, and the changes still waiting run again on top of it with the same ids and time.
- Rows from Realtime that arrive meanwhile go in at once, except on a record a waiting change has changed: that record keeps showing
  the change until its answer.
- The API takes the ids the page offers only for new records: well formed, of the right kind, and found nowhere in the rows it loaded.
  An id that names an existing record is never used, so nothing can be written over this way.

Before: every change waited for its answer, 0.9 s on average on mrdeliveryman.com over the week before, up to 15 s.

Tests: live `tools/supabase/test-live.js` section 14 (the office page with the server's answers held back) and
`tools/supabase/test-r14.js` (the server's side of the ids). The demo already showed changes at once (it has no server).
